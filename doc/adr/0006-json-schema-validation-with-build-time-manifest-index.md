# JSON Schema validation with a build-time Manifest Index for cross-reference checking

All declarative state in the Project Manifest is validated against JSON Schema 2020-12. Cross-references between files use a typed **Reference URN** format (`item:bone`, `block:oak_log`, `mob:zombie`, `scene:<path>`, `script:<path>`). A build-time **Manifest Index** (`.cache/manifest_index.json`) is generated by walking the project's Entity Directories and Registry Files; it maps every URN to its concrete target. The validator uses the index to resolve cross-references and report dangling references as errors.

Validation runs in two places:

- **Agent-side**, after every tool-call mutation. Fast feedback loop; the agent self-corrects when it sees "Reference URN `item:bone` not found."
- **Engine-side**, at project load. Catches drift from external edits (a contributor edited a file by hand and broke a reference) before the project runs.

A single validator library implements both surfaces, tested against a shared fixture corpus.

Engine-shipped schemas live at `engine/schemas/*.schema.json`. User projects reference them via `$schema` URLs pinned to an engine version.

## Considered Options

- **JSON Schema only, structure-level validation per file. Cross-refs unvalidated.** Rejected: dangling references would surface only at runtime, giving the agent no way to verify its own work.
- **JSON Schema 2020-12 plus build-time Manifest Index for cross-reference resolution.** Selected.
- **TypeScript types as source of truth, codegen JSON Schema, tsc-like cross-reference checking.** Rejected for MVP: adds a Node/npm/tsc build pipeline that an OSS contributor has to learn before reading a schema. May revisit post-MVP if schema authoring becomes a maintenance burden.
- **Custom validator framework with its own schema DSL.** Rejected. NIH; loses the JSON Schema ecosystem.
- **No static validation at MVP, runtime only.** Rejected: runtime-only means broken references crash during creator playtests, far from the edit that caused them.

## Consequences

- The agent's tool API must surface validation errors back to the agent in a structured form (file path, error type, expected vs actual). The agent loop incorporates validate-on-write as part of every tool call.
- The same Manifest Index that powers cross-reference validation also serves as the engine's runtime registry lookup. No duplicate work.
- The validator is a load-bearing component. It is implemented once in the language used by the agent orchestration (likely Python) and either re-implemented in GDScript or invoked via subprocess from the engine. Both implementations are tested against the same fixture corpus to prevent drift.
- Schemas live in the engine fork, not in user projects. Projects pin to an engine version. Schema changes ship with engine releases.
- Reference URN grammar is consistent across the project, making the agent's tool calls and the validator's errors predictable.
- Cross-reference type-checking catches a large class of errors statically: deleted items still referenced by recipes, mobs pointing at nonexistent scripts, world-gen referencing missing blocks. None of these can reach runtime if the agent runs the validator on every mutation.
- Schema evolution and migration story is deferred (see open questions).
